# 地理探究伴学智能体技术方案

## 1. 项目概述

“地理探究伴学智能体”面向《中国地质大学（北京）虚拟地理环境实践课程》教学场景，服务对象主要为约 70 名学生及授课教师。当前已完成 MVP，并已上线平台托管版本，用于验证三类核心能力：基于教材的 GIS 实验问答、地理探究问题建模辅助，以及学生探究过程评价。

本方案文档在现有 MVP 基础上，补齐完整的系统设计说明，并纳入已确认的后续迭代方向，便于向技术合作方和委托方（张老师）统一说明当前实现、可扩展边界与下一阶段开发路径。

当前线上地址为：<https://k7m7ilgp.cn-east-fn.bytedance.net/>

## 2. 系统整体架构

### 2.1 架构目标

系统目标不是做一个重后台教学平台，而是优先构建一个轻量、可演示、可逐步扩展的课程伴学智能体。整体设计遵循以下原则：

1. 前端界面尽量简单，围绕课堂真实交互组织功能。
2. 知识库优先基于课程教材，保证回答可追溯。
3. 推理链路保持清晰：输入路由、检索或解析、LLM 生成、结果输出。
4. 预留 L2 GIS 数据体检能力，支撑学生上传真实空间数据后的诊断与修复建议。
5. 后续可以平滑扩展到作业上传、教师驾驶舱和 L3 沙箱执行。

### 2.3 前端设计

当前前端采用 Gradio Web UI，原因是开发速度快、部署简单、适合课堂演示与教师验收。当前 MVP 已实现三个核心 Tab，后续将新增一个“L2 GIS 数据体检”Tab。

现阶段与规划中的前端功能如下：

**Tab 1：GIS 实验助教**

学生输入实验相关问题，系统先从教材知识库中检索相关片段，再调用 LLM 生成回答，并返回命中的教材章节，强调“答案有依据”。

**Tab 2：问题建模助手**

学生输入拟研究的问题，系统基于“六真”课程框架判断问题是否适合做地理探究，并给出收窄、改写和下一步建议。

**Tab 3：过程评价**

学生粘贴探究过程描述后，系统按五个维度进行 0-5 分评分，并给出分项反馈与优先改进建议。

**Tab 4：L2 GIS 数据体检（计划新增）**

学生上传打包后的 Shapefile 数据，系统自动做空间数据体检，输出结构化诊断报告、修复建议，以及可直接复制到 QGIS 或 Python 环境中的修复命令。

### 2.4 后端设计

后端目前以单文件应用形式组织，核心代码位于 `geo_agent/app.py`。从职责上可分为三层：

第一层是知识库与检索层，负责教材解析、切片、向量化、索引和 Top-K 检索。

第二层是业务逻辑层，分别处理 GIS 实验助教、问题建模助手、过程评价，以及后续新增的数据体检逻辑。

第三层是大模型调用层，统一接 OpenAI 兼容接口，对不同功能注入不同 Prompt 模板。

### 2.5 数据流说明

系统主数据流如下：

```text
学生输入
  → 功能路由（实验助教 / 问题建模 / 过程评价 / 数据体检）
  → 检索或解析
      - 问答类：教材检索
      - 数据类：文件解压与空间数据体检
  → LLM 生成或规则诊断增强
  → 输出结果
      - 自然语言回答
      - 评分表
      - 数据体检报告
      - 教材依据或修复命令
```

对于 GIS 实验助教，链路是“提问 → 教材检索 → Prompt 拼接 → LLM 生成 → 输出答案与章节依据”；对于数据体检模块，链路是“上传 ZIP → 解析空间数据 → 生成结构化诊断结果 → LLM 生成修复建议 → 输出报告与命令”。

## 3. RAG 知识库实现

### 3.1 数据来源

当前 RAG 知识库主来源为课程教材：

- `虚拟地理环境实践教程 0922版本.docx`

该文档是当前实验问答的核心知识来源。MVP 中已经基于此文档建立了本地索引。后续如果需要，也可以把与课程方法论相关的 PPT、示例作业、教师讲义等纳入扩展知识库，但首期应坚持“教材优先”。

### 3.2 文档解析策略

文档解析采用 `python-docx`。总体原则如下：

1. 只提取可读文本内容。
2. 跳过图片及无法稳定提取的复杂对象。
3. 尽量保留 Word 中原有的章节标题层级。
4. 章节标题既用于切片边界，也用于后续检索展示。

建议解析流程如下：

1. 读取 `.docx` 文档。
2. 逐段遍历 paragraph。
3. 识别 `Heading 1 / Heading 2 / Heading 3` 或等价中文标题样式。
4. 将标题作为逻辑边界，组织为“章-节-正文”结构。
5. 忽略纯空行、装饰性内容和图片占位。
6. 对正文做基础清洗，例如去除多余空白、规范换行。

### 3.3 切片策略

切片策略是本项目知识库质量的关键部分，后续实现应以本节为准。

#### 3.3.1 逻辑切分原则

以章节标题为主线进行逻辑切分。优先按 `Heading 1 / Heading 2 / Heading 3` 组织结构，每个实验尽量作为独立语义单元。也就是说，切片不能只按固定字数机械截断，而应先尊重教材的实验组织方式，再在实验内部做二次切片。

#### 3.3.2 Chunk 长度目标

每个 chunk 的目标长度设为 **500-800 token**，大致对应 **300-500 汉字** 的正文规模。这样做有两个原因：

一是太短会破坏实验步骤的完整性，召回结果容易碎片化；二是太长会增加无关噪声，影响检索准确性与 Prompt 成本。

#### 3.3.3 Overlap 策略

相邻 chunk 保留 **50-100 token** 的重叠区域，避免实验步骤恰好在边界处被截断。尤其是“步骤 3 接步骤 4”“参数说明接结果解释”这类结构，如果没有 overlap，模型生成时容易漏掉关键衔接。

#### 3.3.4 元数据设计

每个 chunk 建议保存以下元数据字段：

| 字段 | 含义 |
| --- | --- |
| `chapter` | 章名，例如“第三章 土地利用变化模拟” |
| `section` | 节名或实验名，例如“3.2 PLUS 模型参数设置” |
| `page_hint` | 大致页码或位置信息，便于后续人工核对 |
| `text` | 该 chunk 的正文文本 |

如有需要，还可以补充 `chunk_id`、`source_file`、`heading_path` 等内部字段，便于索引维护与定位。

#### 3.3.5 特殊处理规则

对于“操作步骤类段落”，优先保持完整，不在步骤中间断开。例如连续编号的操作说明、参数配置流程、实验结果判读步骤，应尽量落在同一 chunk 内。必要时宁可略微超出标准长度，也不要把关键步骤拆断。

#### 3.3.6 推荐伪代码

```python
for experiment in textbook_structure:
    sections = split_by_heading(experiment)
    for section in sections:
        if is_procedure_section(section):
            chunks = split_with_step_integrity(
                section.text,
                target_tokens=(500, 800),
                overlap_tokens=(50, 100)
            )
        else:
            chunks = split_normally(section.text)
        save_chunks(chunks, metadata={
            "chapter": experiment.chapter,
            "section": section.title,
            "page_hint": section.page_hint,
            "text": chunk_text,
        })
```

### 3.4 Embedding 方案

Embedding 采用三级降级设计，以保证演示稳定性与部署灵活性。

**优先级 1：OpenAI `text-embedding-3-small`**

当配置 `OPENAI_API_KEY` 且网络可用时，优先使用 OpenAI embedding。优点是中英混合与中文表现相对稳定，适合当前教学问答场景。

**优先级 2：sentence-transformers**

若无法调用 OpenAI，则降级到本地模型 `paraphrase-multilingual-MiniLM-L12-v2`。适合离线演示或预算敏感场景。

**优先级 3：TF-IDF**

当本地向量模型下载或加载失败时，进一步降级到 TF-IDF，保证系统至少具备基础关键词检索能力，不至于完全不可用。

### 3.5 向量库与持久化

向量库采用 **FAISS**，索引类型按当前技术方案约定为 **`IndexFlatL2`**。本地持久化文件为：

- `index/kb.pkl`

持久化内容建议包括：

1. chunk 列表与元数据；
2. embedding 向量；
3. embedding 配置；
4. 检索所需索引对象或其可恢复信息。

说明：当前 MVP 代码已经具备本地 `kb.pkl` 持久化能力，后续只需把切片元数据结构按本方案升级即可。

### 3.6 检索策略

检索阶段默认配置为：

- `Top-K = 4`
- 相似度：余弦相似度
- 检索结果拼接后注入 LLM Prompt

检索流程如下：

1. 接收学生问题。
2. 将问题转换为查询向量。
3. 在 FAISS 中召回最相关的 4 个 chunk。
4. 将每个 chunk 的 `chapter / section / text` 拼接为上下文。
5. 把上下文与学生问题一起送入问答 Prompt。
6. 输出回答，并展示对应章节依据。

## 4. L2 GIS 数据体检模块

### 4.1 模块定位

L2 GIS 数据体检模块面向课程中的真实空间数据使用场景。它不是通用 GIS 桌面软件替代品，而是一个“课前体检 + 问题提示 + 修复建议”助手，帮助学生在进入 QGIS、ArcGIS 或 Python 分析前，先发现数据是否能用、问题在哪、如何改。

### 4.2 输入格式与限制

支持的数据格式如下：

- `.shp`，并要求与 `.dbf`、`.prj`、`.shx` 一起上传
- 上传形式统一为 `.zip`
- 文件大小上限：**200MB**

之所以要求 zip 上传，是因为 Shapefile 本身由多文件组成，前端和服务端都更容易做完整性校验。

### 4.3 解析组件

推荐实现组件如下：

- `geopandas`：读取 Shapefile
- `pyproj`：解析与判断坐标参考系（CRS）
- `shapely`：辅助做几何有效性检查
- `zipfile`：解压 ZIP 包
- `pathlib` / `tempfile`：管理临时目录与文件

### 4.4 体检项目

L2 模块至少覆盖以下检查项。

#### 4.4.1 坐标系识别

读取 `.prj` 信息并识别 CRS。如果缺少 `.prj`，需要明确提示“无法自动判断坐标系，需人工确认原始数据来源”。如果识别出为常见投影坐标系或地理坐标系，则进一步判断是否建议重投影到 `CGCS2000` 或 `WGS84`。

#### 4.4.2 空间范围检查

计算数据的 bbox，并结合中国范围阈值判断是否可能落在中国境内。如果空间范围明显异常，例如经纬度落在非中国区域或投影坐标量级明显不合理，应提示“可能存在坐标系误配或投影问题”。

#### 4.4.3 要素统计与几何类型

输出要素数量，并识别几何类型，例如 `Point`、`LineString`、`Polygon` 或混合类型。对于课堂作业，这一步能快速判断学生拿到的数据是否与任务要求一致。

#### 4.4.4 属性字段检查

列出字段名、字段类型、缺失值概况和可疑字段，例如乱码列名、全空列、过长文本列等。字段结构是否清晰，会直接影响后续学生能否继续做空间分析。

#### 4.4.5 空几何与无效几何检查

检查空几何、重复几何、无效几何。对于 Polygon 数据，还应额外关注自相交等常见问题。发现异常时，应给出修复建议。

#### 4.4.6 常见错误提示

至少覆盖以下高频问题：

- `.prj` 文件缺失
- 字段名乱码
- 坐标系未知或误配
- bbox 异常
- Shapefile 组件不完整
- 几何无效
- 编码问题导致属性读取异常

### 4.5 数据体检输出结构

建议输出分为三层：

第一层是**结构化诊断报告**，直接列出文件状态、CRS、bbox、要素数、几何类型、字段信息和异常项。

第二层是**修复建议**，用自然语言说明学生下一步该做什么，例如“先补齐 prj 文件”“先统一投影后再做缓冲分析”。

第三层是**可复制命令**，给出 QGIS 操作提示或 Python 代码，让学生和教师可以直接落地修复。

### 4.6 LLM 诊断 Prompt 模板

以下为推荐 Prompt 模板：

```text
你是地理信息科学课程的数据体检助教。你的任务是根据空间数据的结构化检测结果，生成一份面向学生的诊断报告。

要求：
1. 用中文输出，先给结论，再给问题详情和修复建议。
2. 不夸大问题。能继续使用的数据不要误判为不可用。
3. 如果存在坐标系、几何或字段问题，要明确说明影响的后续分析环节。
4. 修复建议要尽量具体，并给出可复制的 QGIS 或 Python 处理方式。

输入信息：
- 文件名：{file_name}
- CRS：{crs}
- bbox：{bbox}
```

## 5. 三个核心功能模块的 Prompt 设计

### 5.1 GIS 实验助教

#### 5.1.1 功能目标

围绕教材内容回答学生的实验操作问题，重点是“依据教材、步骤清楚、不过度替学生完成思考”。

#### 5.1.2 Prompt 模板

```text
系统角色：
你是“地理探究伴学智能体”，服务对象是中国地质大学（北京）地理信息科学相关课程学生。

回答要求：
1. 用中文，表达清楚，先给结论，再给步骤或建议。

2. 分步操作

```

### 5.2 问题建模助手

#### 5.2.1 功能目标

帮助学生判断一个研究问题是否适合作为地理探究课程项目，并引导问题收窄与研究设计成形。

#### 5.2.2 可探究性判断逻辑

判断标准应围绕“六真”课程框架展开，即：真场景、真数据、真处理、真模拟、真应用、真评价。一个问题是否适合进入课程探究，关键不在于表述是否宏大，而在于是否具备明确对象、合理范围、可获得数据和可执行方法。

#### 5.2.3 Prompt 模板

```text
你是地理探究课程的问题建模助手。请判断学生问题是否适合做课程探究，并给出修改建议。

课程框架：
“六真”课程框架：真场景、真数据、真处理、真模拟、真应用、真评价。

学生研究问题：
{question}

请按以下结构输出：
1. 是否可以探究：可以 / 需要收窄 / 暂不适合
2. 判断理由：从真场景、真数据、真处理、真模拟、真应用、真评价角度简要判断
3. 主要问题：指出研究对象、空间范围、时间范围、数据、方法或评价指标中的缺口
4. 改写建议：给出 2-3 个更适合作为课程项目的问题表述
5. 下一步行动：列出学生下一步要补充的信息
```

### 5.3 过程评价

#### 5.3.1 功能目标

对学生探究过程做形成性评价，不只给分，还要指出问题和改进方向。评分不应“普遍高分”，要能拉开差距。

#### 5.3.2 五维度评分标准

| 维度 | 0-1 分 | 2-3 分 | 4-5 分 |
| --- | --- | --- | --- |
| 问题提出 | 问题模糊，缺少对象、时间或空间边界 | 有基本问题意识，但边界不完整 | 问题明确，具有清晰对象、空间与时间范围，适合探究 |
| 数据准备 | 数据来源不清或明显不匹配 | 数据基本可用，但尺度、格式或预处理说明不足 | 数据类型、来源、尺度和预处理思路清楚，支撑后续分析 |
| 方法选择 | 方法与问题明显不匹配 | 方法基本合理，但步骤不完整或缺少关键参数 | 方法与问题高度匹配，流程清楚，可执行性强 |
| 结论表达 | 结论空泛，缺少证据支撑 | 有结果描述，但解释力度一般 | 结论清楚，能基于结果解释现象，且不过度外推 |
| 反思改进 | 没有反思或只写空话 | 能意识到部分问题，但不够具体 | 能明确局限、误差来源和后续改进方向 |

#### 5.3.3 Prompt 模板

```text
你是地理探究课程过程评价助教。请按评分细则评价学生提交的探究过程。

评分维度，每项 0-5 分，合计 25 分：
- 问题提出：研究问题是否清晰、可探究，是否有明确空间/时间/对象边界。
- 数据准备：数据类型、来源、尺度、格式、预处理思路是否合理。
- 方法选择：模型、GIS 操作或模拟方法是否与问题匹配，步骤是否可执行。
- 结论表达：是否基于结果给出清楚解释，是否避免超过数据支持范围。
- 反思改进：是否说明局限、误差来源、改进方向或进一步验证方法。

学生提交：
{process_text}

请输出一个 Markdown 表格，列为：维度、得分、反馈、改进建议。
表格后给出总分、总体评价和优先改进项。
评分要克制，不能全给高分。
```

## 6. 部署方案

### 6.1 当前部署

当前 MVP 已采用平台托管方式上线，适合教师验收与课堂演示。托管版本的优势是无需本地装环境，打开链接即可访问。

### 6.2 本地部署

本地启动方式如下：

```bash
cd geo_agent
python -m pip install -r requirements.txt
python app.py
```

默认启动地址：

```text
http://127.0.0.1:7860
```

如需修改端口：

```bash
PORT=7861 python app.py
```

### 6.3 环境变量

最关键的环境变量是：

```bash
export OPENAI_API_KEY="你的 API Key"
```

模型调用采用 OpenAI 兼容接口风格，因此也支持替换为国内兼容 OpenAI API 格式的服务。只要接口协议兼容，即可替换底层服务商，而无需重写业务逻辑。

可选环境变量还包括：

```bash
export OPENAI_MODEL="gpt-4o"
export OPENAI_EMBEDDING_MODEL="text-embedding-3-small"
export EMBEDDING_BACKEND="auto"
export TOP_K="4"
```

### 6.4 扩展接口预留

当前部署方案已为后续扩展预留空间，重点包括两个方向。

第一个方向是**学生作业 Word 上传接口**。后续学生可直接上传探究报告、实验说明或阶段性作业，由系统自动做摘要、评价、对照评分。

第二个方向是**教师驾驶舱**。未来可面向教师增加班级整体问题热度、常见数据错误、学生选题分布、评分统计等视图，用于课堂管理与教学反馈。

## 8. 现状与实现边界说明

为避免方案和现状脱节，需要明确区分“已实现”和“已规划”。

当前代码仓 `geo_agent/app.py` 已实现三类核心功能、教材解析、本地索引持久化和基础 Gradio UI。当前索引文件已采用 `geo_agent/index/kb.pkl` 形式存储，并具备 embedding 降级逻辑。

但本方案中关于“按 Heading 1/2/3 保留完整章节层级的切片元数据”“L2 GIS 数据体检模块”“Top-K=4 固定配置”“IndexFlatL2 统一约定”等部分，属于下一阶段需要按方案落地或升级的内容。这样写的目的是把当前 MVP 和后续迭代纳入同一份技术方案中，便于后续开发、沟通和验收。

## 10. 总结

“地理探究伴学智能体”的价值不在于做一个大而全的平台，而在于为地理探究课程提供一个真正贴近课堂流程的 AI 助教工具。当前 MVP 已经验证了三条关键链路：教材问答、问题建模和过程评价。下一步最重要的增量，是把真实空间数据接入进来，补齐 L2 GIS 数据体检能力，让系统从“会回答”进一步走向“会看数据、会指出问题、会给修复建议”。

从技术路径看，这个项目适合继续沿着“轻前端 + 本地知识库 + OpenAI 兼容模型 + 可控扩展模块”的路线推进。这样既能控制复杂度，也便于在课程教学场景里持续打磨。
